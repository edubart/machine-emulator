## Process deviations and notes

- **An earlier audit's report was in the tree.** Commit `20a788c` carried an `AUDIT_REPORT.md` of a completed audit of
  another branch (`feature/prt-audit`), while `BUGS.md` was the empty template and `bugs/` did not exist. `AUDIT.md`
  makes `AUDIT_REPORT.md` the campaign state, so the orchestrator opened it to resume, and read about the first half of
  it (summary, process, and the candidate tables of its early rounds) before recognizing it as the report of an earlier
  audit, which the blind-hunt rule forbids reading. It stopped reading there and replaced the file with this one. The
  old text remains in git at `20a788c`. Consequences and mitigations:
  - No agent of this campaign is given anything from that report. Every agent is told not to read the history of
    `AUDIT_REPORT.md` or `BUGS.md` before this campaign's first commit.
  - The orchestrator derives every angle from `THREAT_MODEL.md` and the strategies `AUDIT.md` prescribes, not from what
    it read. It only orchestrates, so it proposes no candidates itself.
  - The requester should treat the orchestrator, not the hunters, as non-blind.
- **Round order and overlap.** The requester asked for at least 10 rounds in two days. To keep that pace, round 2
  (data flow) hunts while round 1 is still in triage and proof, so its hunters got round 1's candidates with the outcome
  "pending". The variant search for confirmed bugs, which `AUDIT.md` lists second, runs as round 3, once round 1 has
  confirmations. Hunts run as several workflows side by side to reach 10 concurrent hunters. No hunter was blocked in round 1.
- **Disk filled once.** During round 1 proofs, anvil instances started by agents dumped block states under
  `~/.foundry/anvil/tmp` (one grew 12 GB in 6 minutes) and filled the disk. The orchestrator removed the dumps, killed the
  runaway anvil (the prover of R1-A7-2 was using it) and added `bugs/harness/anvil-wrap.sh`, which bounds the dumps. Agents
  running at that moment may have seen write failures.
- **Concurrency.** The workflow runtime caps concurrent agents at the CPU count minus two, which is 2 on this 4-CPU
  container, below the 10 hunters `AUDIT.md` allows.

## Gaps and ambiguities in the threat model

Raised by round 1 triage (each names the candidate that exposed it):

- Component table vs section 3: AUDIT.md assigns 'Referee verifier' to machine-solidity-step as a whole, while section 3 defines a referee verifier as one 'whose acceptance settles disputes' and support as 'copies of the verifiers whose acceptance settles nothing'. MetaStep.step in that library is never called by pinned Dave (R1-R11-1: Critical vs Medium).
- Clock sizing in the referee model: unclear whether a deployed referee's clocks sized below the worst-case R12 cost count as a defect that 'only changes how long a claim may take to respond' (support, Medium) or as an A7 failure caused by the emulator's worst-case cost (Critical). Also, section 2 bounds a correctly designed application's mcycles only, not its uarch cycles per mcycle or its input count (R1-A7-1, R1-R12-1, R1-A7-2).
- A5's 'No party can make it stop accepting them': unclear whether a privileged role the deployment configures (the rollups guardian, foreclosure) is such a party or a trusted part of the deployment (R1-A5-1).
- Section 4 says 'the manual must state this requirement', which is a requirement on the manual. No section 8 case says whether violating it is Medium ('violates a rule or the manual') or Low (R1-R14-2).
- O1/section 4: unclear whether a snapshot whose hashed contents meet every valid-template condition must stay adoptable when its cached hash-tree structure is malformed or missing, and whether a loud load error counts as 'crash the honest operator'. Non-hashed config.json fields such as hash_tree.phtc_size are neither 'cached hash-tree data' nor a valid-template condition (R1-O1-1, R1-O1-2).
- R4 configuration clause: unclear whether it binds independently of the valid-template conditions, and whether 'register values' covers uarch RAM contents given in a configuration (R1-R4-1).
- R13 'reproducibly buildable': unclear whether this requires pinned build inputs (toolchain versions, base-image digest) or only that today's rebuild matches. The High case's qualifier 'while what is deployed matches its audited source' is also ambiguous when the audited source cannot be built without a hand edit (R1-R1-1, R1-R13-1).
- Output/yield exclusion: unclear whether it excuses a per-yield cost that is bounded but larger than needed, and whether it covers console characters, which are neither outputs nor yields (R1-R8-3, R1-R14-1).
- Referee-model input record: unclear whether the input files given to the doc/recipes referee stand for the on-chain input record that any sender fills (rated as if a deployed referee had the defect) or are trusted configuration (R1-A2-1).
- R1 'Undefined behavior': unclear whether a data race or out-of-range write whose value no hash ever reads violates R1 by itself (R1-R9-2).
- Section 5 calls any disagreement between Dave and the manual's model a defect. Section 8 gives no class to a disagreement that changes no outcome, such as Dave letting anyone join inner tournaments (R1-A2-2).
- Section 3 says referee-model stalls are 'rated as support', and the support rule gives Medium when the stood-in role (a deployed referee breaking A8) would be Critical. That makes 'rated as support' almost always Medium, which may not be intended (R1-A8-3).
- Guest software 'documented use' is undefined for implicit dependencies: undocumented /tmp/merkle.dat state, and --utf8-payload with untrusted payloads although the manual's own calculator uses that mode (R1-GUEST-1, R1-GUEST-2).
- Deliberate API state change 'performed as documented': unclear when the API accepts a write to a register the manual calls 'a creation-time mode' (iunrep) (R1-R2-1).
- SHA-256 machines: R9 requires precomputed hashes to be correct for 'every supported hash function', but the manual reserves SHA-256 for the ZK prover and AUDIT.md excludes ZK proving (R1-R9-1).
- Blind-hunt rule vs R13: proving that released versions collide on machine-identification registers requires reading release tags, which are neither audit/prt2 history nor clearly 'other branches' (R1-R13-3).
- Host support: the Medium case for loud persistence failures in an 'uncommon host setup that the manual documents' depends on which hosts the manual documents, and doc/README.md names no supported OS or page size (R1-R1-2).

Raised by round 2 triage:

- Self-contradictory manual: section 8's clause 'It takes the severity it would have if the manual were right' does not say which statement governs when two manual sections contradict each other and the code matches one of them (R2-DFINPUT-1: /dev/cmio section vs HTIF section on REASON/DATA).
- Medium case vs R7: the Medium case for 'an undocumented deterministic deviation, consistent across all paths, in behavior that no correct guest relies on' conflicts with R7's statement that in its listed areas 'any deviation lets an input subvert a correct guest, even a deviation that is consistent across all paths'; also unclear whether the manual's 'support the Sv39 mode' is exhaustive for optional spec features such as Sv48 (R2-DFGUESTSTATE-1; same pattern as R1-R7-2).
- Store sharing modes and O1: unclear whether storing with sharing none/config (documented rollback semantics that copy the initial backing files) is on the honest operator's path, and whether R9's 'every snapshot the emulator itself writes' covers a rollback copy that re-emits the foreign cached hash-tree data an O1 rebuild discarded (R2-DFSTORED-1).
- Attributes outside the hashed state: unclear whether file mode bits, link counts and backing-file lengths of a template are things 'it carries outside the hashed state' that may not 'crash the honest operator', and whether R4 is met when one adoption path (unshared load then store) works while the documented clone path fails loudly (R2-DFSTORED-2; related to R1-O1-1).
- R12 'nearest retained input boundary': the model does not say how many input boundaries the honest operator must retain; 'which the application's per-input usage bounds' implies one per input, but an operator that retains fewer is not explicitly forbidden (R2-DFINPUTCOUNT-1).
- Constant-factor High case scope: it covers only 'an operation listed in R12', so constant-factor memory or time overheads in the honest operator's work outside the emulator (chain observation, records) have no class beyond R12's per-input bound (R2-DFCHAIN-1). The outputs/yields exclusion's 'each yield costs it a bounded amount' still leaves open whether a bounded but guest-declared per-yield cost (2 MiB payload copied without the guest writing it) is excused (R2-DFYIELD-1; extends the R1-R8-3 gap).
- Supported deployment shapes: the model does not say whether the honest operator must support an application whose input record starts before its consensus contract exists (ApplicationFactory app with a later DaveConsensus), which decides Medium vs Low (R2-DFINPUTCOUNT-2).
- Genesis vs non-genesis templates: section 2's valid template allows a tx buffer with prior outputs, while the manual says 'A template is the genesis of a Cartesi Rollups application' and DaveConsensus seals epoch 0 with a zero outputs root; unclear whether PRT deployments must support non-genesis templates (R2-DFOUTPUT-1).
- Section 5's 'Any other disagreement between a deployed referee and the model is a defect' still has no class when the disagreement changes no outcome; R2-DFCLAIM-1 extends R1-A2-2 from joins to every match move (who may open, seal, prove a leaf, or claim a timeout win).
